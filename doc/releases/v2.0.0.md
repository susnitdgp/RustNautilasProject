# Release v2.0.0

Release date: 23 September 2026 (IST).

**Versioned engineering snapshot; not approval for unattended live trading.**

## Included since v1.0.0

- Native Trend Ribbon [BOSWaves] and Pivot Point SuperTrend selections, sharing the Nautilus LiveNode and guarded Kite execution path.
- Explicit manual production launchers, strategy and broker configuration checks, and session execution gates.
- WebSocket-triggered broker reconciliation, bounded read retries, durable order ownership and no automatic order resubmission.
- Pivot flat-position recovery correction; historical rebuilds cannot replay old entries.
- Engineering design documentation, test coverage and a pinned Kite candle fixture for 18, 21 and 22 September.

The final release preparation changes configuration paths, documentation and application version metadata only. It does not fix the trading-behavior limitations below.

## Configuration migration

The active Trend Ribbon launcher still reads `config/production-trend-ribbon.json` and the locally managed `config/kite-production.json`.

Four optional JSON presets are now under `config/backup/`: `pivot-point-supertrend.json`, `production-pivot-supertrend.json`, `production-supertrend.json`, and `trend-ribbon-boswaves.json`. Their contents and live-order flags are unchanged. Archiving a live-enabled preset does not disable it.

Optional launchers, source defaults, tests, service templates and documentation use the new paths. Existing TOML files remain in place. External scripts using an old preset path must be updated. Candidate-package scripts deliberately retain their own packaged `config/production-supertrend.json` layout.

The application package `kite-node` is version `2.0.0`; internal library crate versions and pinned dependencies are unchanged. The annotated `v2.0.0` Git tag identifies the complete workspace snapshot.

## Known limitations retained in this release

1. **Pine session-reset mismatch.** The uploaded Pine sets `trend := 0` when mandatory square-off fires. Current Rust Trend Ribbon retains its indicator direction. The implemented numerical formulas and intraday regression do not establish equivalent next-session entries.
2. **Trend Ribbon cutoff without quotes.** The dedicated quote-independent square-off timer is registered for Pivot only. Trend Ribbon has run-deadline and quote-driven handling, but reliable reducing exits during a quote outage at cutoff are not established.
3. **Validation boundaries.** The 17-flip fixture protects the current Rust result on pinned Kite candles; the screenshot comparison is not a TradingView numerical export. Real broker fills, full-session operation and exact TradingView parity remain unverified.
4. **Legacy diagnostic wording.** Shared production checks still contain some Pivot/Supertrend wording. A successful offline configuration check does not validate broker positions, funds, credentials or execution readiness.

The configured production execution cutoff remains 23:00 IST for the regular 23:30 market-calendar close; the Trend Ribbon paper signal session ends at 23:15. These are configuration/execution policies, not guarantees of successful broker fills or completed flattening by a timestamp.

## Build and validation

```bash
cargo fmt --all -- --check
cargo test --locked --workspace --features kite-adapter/live-orders -j 3
cargo clippy --locked --workspace --all-targets --features kite-adapter/live-orders -- -D warnings
cargo build --locked --release -p kite-node --features kite-adapter/live-orders -j 3
```

The `live-orders` feature makes the binary capable of broker order submission after runtime gates pass. Compilation and configuration checking do not start a trading node. Release publication does not start, restart or install a service.

The prior local production binary is retained separately as a rollback artifact. The release bundle is built from the tagged Git snapshot, not by archiving a dirty working tree. Private working copies of `config/kite-production.json` and `config/kite-sandbox.toml` are excluded from release staging and packaging; only their committed defaults may appear in the Git source archive.

A release tag is a source reference. A GitHub Releases page is a separate publication operation and is not implied by pushing the tag.
